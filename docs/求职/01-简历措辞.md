## 1. 前端岗（3 条 / 6 条两版）

### 3 条版（空间紧张时用）

- **搭建设计系统并做到换肤不动页面代码**：把颜色、间距、圆角、字体、卡片/按钮/导航等样式全部收进 5 套主题 token（`Theme` 类型 + `useThemedStyles`），页面只消费 token，新增主题只需加一份配置，**5 套主题共 0 处页面改动**。
- **一套代码同时跑 iOS / Android / Web**，处理 RN-web 的平台差异：定位并修掉两类只在 Web 出现的布局 bug（`position:absolute` + `left/right` 与 tabBar 自带 `width:100%` 冲突导致第 5 个 tab 溢出屏幕；图片同时写 `width:100%` 和 `flex` 导致拼贴布局被第一张挤满），修复后 390px 宽度下 5 个入口全部可见。
- **为「长任务」做前端状态机而不只是 loading**：试穿/视频是 40 秒–25 分钟的异步任务，实现了串行任务链（1–3 件逐件推进、显示 1/3、2/3 进度）、断线续看（任务 ID 落地本地，重开页面自动接管轮询）、以及单视频三重门控（页面聚焦 && App 在前台 && 当前页）避免切 tab 后视频还在响。

### 6 条版（正文放得下时用）

在上面的基础上再加：

- **统一错误文案层**：所有网络错误经 `toUserMessage()` 映射成中文可操作提示（「网络不太稳，请检查网络后重试」/「请求超时了，请重试」/「生成还在后台进行，稍后到「我的」看结果」），消除把 `TypeError: Failed to fetch` 直接甩给用户的问题。
- **自建 CDP 巡检工具**：用 Chrome DevTools Protocol 写了一个小工具，逐路由收集 console error / 未捕获异常 / 4xx 请求 / 裂图（`naturalWidth === 0`），**8 个页面覆盖，最终 0 裂图 / 0 异常 / 0 失败请求**，并据此定位到「天气一直不可用」的真因是上游 IP 定位服务被限流（429）。
- **可访问性与触控**：删除类危险操作补 `accessibilityLabel`、触控区从 26px 提到 44px、危险动作二次确认。

## 2. 全栈岗（3 条 / 6 条两版）

### 3 条版

- **独立完成「客户端 → 边缘函数 → AI 供应商 → 存储」四层链路**：前端 Expo RN 三端同构；5 个 Supabase Edge Functions（Deno）承载试衣、图生视频、对话、背面素材、支付；22 个数据库迁移（1.1k 行 SQL）管理表结构与 RLS；密钥只存在边缘函数，前端仅持有 anon key。
- **用对照实验证明并修掉一个真实的 RLS 漏洞**：拿两个新注册的匿名身份 A/B 做探针——修复前 B 能往 A 的目录上传、能删 A 的文件、未登录能列举照片桶并读到 17 条含他人照片地址的任务行；根因是旧宽策略残留（PostgreSQL 的 RLS 是「任一策略通过即放行」），修复后同一批探针**全部 403 / 返回空数组**，并把写入权限收归 service_role。
- **存储私有化后把整条链路改对**：桶一私有，供应商拿 URL 下载图片全部 400。方案是「库里存不含 token 的规范地址，只在看图和调供应商那一次签 1 小时地址」，并做了签名缓存（提前 5 分钟续签）、并发去重、批量签名；删除逻辑改成「先删行确认影响 1 行，再清媒体，失败降级为警告」，避免「文件没了但记录还在」。

### 6 条版

再加：

- **失败路径设计**（这个项目最贵的三次教训）：① 同步接口给了 20 秒超时、供应商要 40–70 秒 → 用户看到「生成失败」而服务端照跑照扣费，修成 180 秒 + 文案改「还在后台生成」；② 视频轮询超时判断写在查供应商之前，导致**已经出片的视频在第 10 分钟被判死**（实测排队可达 25 分钟），改成查完再判 + 阈值 30 分钟；③ 删除记录先删文件后删行，行删失败时媒体已永久丢失，顺序反转。
- **成本与限流落到代码**：单张试衣 ¥0.4、三件串行 ¥1.2，因此设备限流设成「3 次 / 10 分钟」正好等于单次上限；限流 RPC 从 anon 收回执行权，只给 service_role。
- **匿名身份设计**：无账号体系（安装级设备 ID + 匿名会话），并针对「清缓存即丢历史」补了 12 位恢复码（服务端只存 SHA-256、走 definer 函数、接回时迁移任务/作品/权益三张表）。

## 3. 产品岗（3 条 / 6 条两版）

### 3 条版

- **用「信任配额」重排信息架构**：原底栏是 首页 / 对话 / 发布 / 试衣 / 我的，其中「对话」依赖的外部服务当时整体不可用，每次点开必报错却占着一级入口。决策是把「搭配」提上来、把「对话」降级到搭配页底部（路由与代码全保留），理由是「一个每天报错的入口，比一个没有入口的功能更伤体验」。
- **把「三件衣服」压缩成「一次操作」**：商业试衣模型只吃「一张人像 + 一件衣服」，用户要自己记着试完上装再试下装。改成串行叠加（第 N 步拿第 N−1 步的结果当新的全身照）后，用户一次选 1–3 件即可，代价是 3 件约 3 分钟、¥1.2，用「1/3、2/3 进度」把等待变得可解释。
- **补上「生成完然后呢」的闭环**：结果图一键发布到首页灵感流并自动关联单品，别人看到就能点「试穿同款」；发布时会复制一份公开副本到公开桶（结果图本身在私有桶、签名地址 1 小时过期，直接存 URL 会裂图）。

### 6 条版

再加：

- **把「看起来是 bug」的问题当产品问题查**：用户反馈「记录全没了」，排查后不是代码错，而是匿名身份只存在浏览器本地、换 profile 就是一个新人。于是补了恢复码（截图存串码，换设备输码接回），这才是根因层的解法。
- **单位经济**：单张试衣 ¥0.4、单条 5 秒视频 ¥0.3–0.5、问答 ¥0.001/次，据此把套餐设计成 10 次 ¥9.9 / 50 次 ¥39.9，并发现原「会员不限量」套餐在限额缺失时一天可被刷到 ¥172.8 成本 —— 定价必须建立在限流之上。
- **背面不是模型能力问题，是素材完整度问题**：AI 试衣只还原正面视角，用背面图再跑一次会被当成正面「穿反」。最终方案改成「展示实物背面图」，并让用户在视频末尾一键把背对镜头那一帧存成该单品的背面素材，零额外成本。

## 4. 写简历时的自我检查

1. **每条 bullet 是否都有一个数字或一个具体后果？** 没有就删掉或补上。
2. **是否有「负责 / 参与 / 协助 / 了解」？** 有就换成「做了 X，机制是 Y，结果是 Z」。
3. **是否能被追问三层？** 例如「三端同构」→ 追问「Web 上遇到什么坑」→ 追问「你怎么定位的」。答不上来的 bullet 不要写。
4. **有没有把「设计完成」写成「已实现」？** 面试官一验证就露。诚实标注「未验证」反而加分。
5. **三份材料数字是否一致？** 简历说 40–70 秒，PPT 就不能写 30 秒。
