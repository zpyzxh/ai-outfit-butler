# AI 穿搭管家 — 迭代报告（2026-11-16）

本轮目标：**在这个已有项目上继续迭代 —— 修掉真实缺陷、补齐用户要的核心能力（推荐穿搭 / 整套试穿 / 生成图与视频），并把界面收敛成"时尚简约"。**

验证方式：`tsc --noEmit` 全量通过；用 CDP 驱动无头 Edge 逐页截图（390×880 @2x）核对渲染与真实数据；后端能力以静态审计（两个只读审计：服务端 / 客户端）为据，未连线上库做写操作。

## 二、新增能力

### 1. 搭配推荐引擎（`src/lib/outfits.ts`）

不调用任何接口，纯函数，输入衣橱 + 当天气温 + 用户风格档案，输出排序后的搭配。

- **角色识别** `roleOf()`：连衣裙 / 外套 / 上装 / 下装，`category` 缺失时回退到名称正则。
- **色彩分组** `colorFamily()`：`LIGHT_NEUTRALS`（白米奶驼杏燕麦象牙沙浅灰）→ light，`DARK_NEUTRALS`（黑藏深炭墨咖灰棕）→ dark，其余 → accent。
- **组合**：连衣裙（可叠外套）、上装 × 下装（可叠外套），无法组合时降级为单品推荐。
- **评分**（可解释，不是黑盒）：基础 10；件数加分；无彩色 +1.5 / 单彩色 +0.5 / 双彩色 −2；体感温度分 4 档（hot ≥26 / warm ≥20 / mild ≥14 / cold <14），热天给「亚麻/短袖/雪纺」加分、「羊毛/针织/西装」减分并压外套，冷天反向；气质与场合命中各 +1.2 / +1。
- **文案**：`reason` 用中文句式生成（例：「『奶白针织长袖』配『驼色百褶阔腿裤』，外搭『米色羊毛西装外套』压住整身，中性色打底，稳妥耐看」），`tags` 取命中最多 2 个气质词。

> 为什么用规则引擎而不是大模型：一是不引入外部依赖与费用（当前 chat 依赖的百炼已停服），二是搭配的"合理"本质是**可解释的约束满足**（色彩中和、冷热匹配、场景适配），规则比黑盒更可控、可调试、可离线。

### 2. 搭配页（`src/app/(tabs)/outfits.tsx` + `src/components/OutfitCard.tsx`）

- 头部：`STYLE EDITOR` 眉标 + 衬线 30px「今日搭配」+ `11 月 16 日 · 周一` + 天气胶囊。
- 风格档案条：展示「通勤 · 极简」，点开底部抽屉（`StyleProfileSheet`）改性别 / 气质（≤3）/ 场合（≤3），保存后重新出 3 套。
- 推荐区：`为你挑了 3 套` + `换一批`（seed 递增）+ 一句体感提示；卡片是 **1–3 张单品的编辑式拼贴**（3 件时主图 1.5 : 右列 1:1），角色胶囊（上装/下装/外套）叠在图左下，标题衬线、理由正文、`# 标签`，黑色胶囊「试穿这套 →」。
- 单品精选：横向 116×152 缩略图，点进试衣并预选该单品。
- 三态：骨架屏 / 中文错误 + 重试 / 空态引导。

### 3. 整套串行试穿（`src/app/(tabs)/tryon.tsx`）

关键决策：**不改后端接口**。现有 `tryon` 函数只吃「一张人像 + 一件衣服」，所以第 N 步把第 N−1 步的结果图当作新的全身照传进去，前端串成流水线：

```
全身照 → 上装 → （外套）→ （下装）→ 结果图 → 选姿势 → 图生视频
```

- 上限 3 件：设备限流正好是 3 次 / 600 秒，再多会被服务端拒；超出时提示「一次最多试 3 件，先取消一件再选」。
- 每步显示 `第 2/3 件 · 外套`、已等待秒数、进度条，并提示「单张约需 40–70 秒，请勿离开」。
- 中间结果缩略条保留，任一步失败可从头重跑；轮询连续 3 次网络错误就中止并提示去「我的」看结果，而不是无限转圈。

> 已知限制：串行 3 步 ≈ 3 分钟，Edge Function 的 wall clock（Free 150s / Pro 400s）与设备限流都卡在这个量级。真正的解法是后端的 **advance-on-request** 状态机（见路线图），前端这套 UI 已经按"分步"做好了。

### 4. 「我的」改版（`src/app/(tabs)/profile.tsx`）

三宫格统计（已完成试穿 / 收藏单品 / 收藏搭配）→ 风格档案条 → 试穿记录（缩略图 + 名称 + `分类 · 月/日` + 状态 + 删除）→ 收藏单品横滑 → 界面风格 5 套色卡 → 更多入口（搭配师 / 套餐 / 素材管理）→ 隐私说明 → 账号区。

- 用 `useFocusEffect` 刷新：试完切回来就能看到新记录（原来只在挂载时拉一次）。
- 监听 `profile.userId` 变化清空列表：换账号不会看到上一个人的记录。
- 删除加同步锁 + 触控区 44px，双击不再报「没有删除权限」的假错误。

## 四、界面：为什么这样改

设计基线是项目里已有的 `runway`「时装白」主题，本轮只做"更克制"，没有推倒重来：

- **衬线大标题 + 全大写小字眉标**：`今日灵感` / `今日搭配` / `虚拟试衣` / `我的`，页眉统一走 `STYLE JOURNAL · AI 穿搭管家` 这类杂志式眉标。
- **发丝线分栏**（1px `#E9E9EC`）替代卡片阴影，留白优先。
- **黑胶囊 = 唯一强动作**：`试穿同款` / `试穿这套` / `生成试穿效果` / `发布到首页`，其余都是描边或纯文字。
- **浮动黑胶囊底栏**（62 + 10 高，圆角 22，FAB 上浮），选中态是"图标被 1px 圆环圈住"，不依赖实心变体。
- **骨架屏 + 空态 + 错误态**三态齐全，每个错误态都有可点的重试。
- 5 套主题（时装白 / 纸感画报 / 冷灰水泥 / 夜场黑金 / 宋式留白）在「我的 → 界面风格」可切换，所有新页面都用 `makeStyles(theme)` 从主题取值，没有硬编码颜色。

## 六、还没做 / 建议下一步

按性价比排序，详细方案见 `docs/后端优化路线图.md`：

1. **开 Anonymous sign-ins 并应用 013/014** —— 否则安全收口与「我的」正确性都悬着（P0）。
2. **视频/对话换提供方**（百炼已停服）：`chat` 换任意 OpenAI 兼容服务，`video` 加「提交 + 轮询」适配层，`tryon_tasks.provider_task_id` 加 `ark:` / `kling:` 前缀。
3. **整套试穿后端化**（advance-on-request）：POST 只跑第 1 步，返回 `status=step_done`，前端再 POST `{action:"advance"}`，规避 Edge 150s wall clock；顺带把 `step_index/step_total/entitlement_id` 落库，按步扣配额、失败退款。
4. **幂等与状态机**：`tryon` / `video` 加 idempotency_key + CAS 终态写入（现在是 `.eq('id')` 裸更新，timeout 可能覆盖 done）；`/video` 的重复提交守卫是 TOCTOU。
5. **私有桶 + 签名 URL**：`user-photos` / `tryon-results` 转私有，客户端 `createSignedUrl(3600)`，Edge 内用 service_role `download(path)`。
6. **任务收敛定时器**：用 cron 扫 `processing` 超时任务，而不是靠用户开着页面轮询。
7. **发布与试穿打通**：发布时让作者选关联单品，首页「试穿同款」才不会永远只出现在内置素材上。
8. **匿名身份可迁移**：邮箱登录时 `updateUser` 原地升级 uid，或登录后把匿名任务迁移到新 uid，避免"登录一次历史全丢"。

## 七、第二轮（11-16 下午）：真实联调 + 打通两个闭环

百炼账户充值后做了两次真实调用，确认停服是账户问题而不是代码问题。

### 7.1 实测结果（不是推测）

| 调用 | 端点 | 结果 | 耗时 | 花费 |
|---|---|---|---|---|
| 穿搭问答 | `POST /functions/v1/chat` | 200，返回中文搭配建议 | 3.8s | 约 ¥0.001 |
| 图生视频 | `POST /functions/v1/video` | 200，任务进入 processing | 5.4s | 约 ¥0.2–0.5 |
| 视频终态 | `GET /functions/v1/video?id=…` | `status=done`，`result.mp4` 已转存 | 约 25 分钟后 | — |
| 结果可访问 | `GET …/tryon-results/<id>/result.mp4` | 206，`content-type: video/mp4` | — | — |

结论：**试穿（Aidge）→ 图生视频（通义万相）→ 转存 → 播放**这条主链路是通的，之前的「生成失败」确实是账户欠费。
一个副作用发现：万相排队时长可达 25 分钟，而客户端原来的上限是 10 分钟 —— 用户会在任务还在跑的时候看到失败提示，然后重复提交（重复计费）。已修。

### 7.2 闭环一：从「今日搭配」直接整套试穿

之前搭配页的「试穿这套」只传 `garmentId`（单件），整套搭配的语义在跳转时丢失。

- `src/app/(tabs)/outfits.tsx:121` 改为传 `look=<id,id,id>` + `lookTitle`。
- `src/app/(tabs)/tryon.tsx` 的 `useLocalSearchParams` 支持 `look` / `lookTitle`，进入即预选（上限仍是 3 件），并按 `ROLE_ORDER` 自动排成「上装 → 外套 → 下装」。
- 选品区顶部出现说明条：`来自搭配「层次感叠穿」，会按上装 → 外套 → 下装顺序逐件叠加`。
- 三种入口共存：首页「试穿同款」= 单件、搭配页「试穿这套」= 整套、底栏「试衣」= 空手选。

### 7.3 闭环二：发布的灵感可以关联单品

原来 `inspiration_posts` 没有 `garment_id`，社区作品的「试穿同款」永久缺失，这个 CTA 只对内置素材有效。

- 新增 `supabase/migrations/015_link_inspiration_to_garment.sql`：加 `garment_id uuid references garments(id) on delete set null` + 部分索引。用 `set null` 而不是 `cascade`，下架素材不会连带删掉用户内容。
- `src/lib/inspirationUpload.ts`：`publishInspiration(media, caption, garmentId?)`，015 未应用时报错信息含 `garment_id` 就自动退化成不带关联的插入（发布不会因为后端没升级而失败）。
- `src/app/(tabs)/create.tsx`：配文下面加「关联单品（可选）」横滑选择器（缩略图 + 名称 + 选中描边）+ 说明「关联后，别人在首页看到这条作品就能直接「试穿同款」」。
- `src/lib/supabase.ts`：灵感流字段列表动态拼（`garmentLinkSupported` 开关，缺列自动回退），映射 `garmentId`，带关联的作品副标题显示「社区发布 · 可试穿」。

### 7.4 顺带修掉的

- 视频轮询上限 10 分钟 → 30 分钟（`MAX_VIDEO_WAIT_MS`），并加提示「视频通常需要 3–20 分钟，可以先去别的页面，稍后回「我的」看这条记录」。
- `withRetry` 预算收紧到 6.5s × 2 次（约 13s），避免弱网时骨架屏停留半分钟以上。

## 八、线上库安全收口（2026-11-16 晚，已执行并验证）

### 8.1 为什么要做

匿名登录一直是**关**的（`POST /auth/v1/signup` 返回 422 `anonymous_provider_disabled`），
所以 Edge Function 里 `resolveUserId()` 一直拿到 null，`tryon_tasks.owner_user_id`
**17 行全是 null**，而 012 的 Storage 策略要求 `authenticated` + 路径首段 = uid ——
**新装用户 100% 传不上全身照**。

### 8.2 实测出来的两个真问题

用全新匿名账号做探针（`cdp.mjs eval`，跑在 App 页面上下文里）：

| 探针 | 收口前 | 收口后 |
|---|---|---|
| 上传到自己目录 `user-photos/<uid>/` | 200 | 200 |
| 上传到**别人**目录 `user-photos/<别人uid>/` | **200（可写）** | 400 / 403 `row-level security` |
| 删除**别人**的文件 | **200（真被删掉）** | 400 / 403 `Access denied` |
| 未登录 list 整个桶 | **200，能枚举文件名** | 200 但返回 `[]`（RLS 过滤） |
| 客户端写 `tryon-results` | — | 400 / 403（只能 service_role 写） |
| 未登录读 `tryon_tasks` | 17 行 | 0 行 |

根因不是 012 写错，而是 **001 时代的老策略还留在库里**：PostgreSQL 的 RLS 是
「**任一**策略通过即放行」，所以 `to authenticated using (bucket_id = 'user-photos')`
这种宽泛策略把 012 的 owner 校验完全架空了。

### 8.3 落地内容

- `supabase/migrations/013_security_hardening.sql`（重写第三节）
  - 新增 **策略全扫**：遍历 `pg_policies`，把 `user-photos` / `tryon-results` 上
    **所有**旧策略（不分名字、不分操作）先 drop 掉，再重建 owner 作用域的
    read / write / delete。
  - 限流 RPC 的 `revoke` 改成按实际签名动态执行（见 8.4）。
  - 素材桶只清 SELECT 策略，写策略保留（管理端上传依赖它）。
- `supabase/migrations/014_lock_tryon_tasks_to_owner.sql`
  - 新增 `read legacy ownerless tryon_tasks` / `delete legacy ownerless tryon_tasks`
    两条策略：无主历史行仍可读可删，否则「我的」页会一上来就空白、
    删除按钮永远报没权限。
- `supabase/manual-apply-2026-11-16.sql`：把 013 + 014 + 015 合成一份可直接粘的清单，
  末尾附「可选认领」（把无主历史划给最近创建的匿名用户）。
- `src/app/(tabs)/profile.tsx`：`loadHistory()` 里先 `await ensureSession()`。
  014 之后没有会话就一行都查不到，首装用户可能匿名登录还没走完。

### 8.4 踩到的两个坑

1. **`42883 function public.consume_edge_rate_limit(text, text, integer, integer) does not exist`**
   线上 011 的定义是**三个**参数 `(p_rate_key text, p_limit integer, p_window_seconds integer)`。
   写死四个参数的 `revoke` 直接报错，把整个 013 事务一起回滚（库里什么都没变）。
   改成 `for fn in select p.oid::regprocedure ... loop execute format('revoke all on function %s ...', fn)`。
2. **桶名写错**：代码里是 `inspiration-posts`，我在 013 里写成了 `inspiration-media`。
   由于 013 判断策略用的是 `ilike '%inspiration-media%'`，这段等于空转（不会报错，
   只是没生效）。已修正。线上影响为零：`revoke select on storage.objects from anon`
   已经让未登录无法枚举任何桶，而 `inspiration-posts` 的 authenticated 读策略仍是
   原来那条（语义等价）。

### 8.5 验证

## 十、存储私有化（2026-11-16 深夜）

### 10.1 目标与约束

用户要「企业化」但成本不能上去，所以方案必须满足：
**不新增任何付费组件**（不接 CDN、不上 WAF、不买对象网关），只靠 Supabase Storage 自带能力。

企业化的最小正确做法就是：**私有桶 + 短时签名直链**。
`createSignedUrl` 不额外收费、不产生额外出网流量，只是把「永久公开地址」换成「1 小时有效的地址」。

### 10.2 为什么没有直接把 user-photos 改私有

试过，走不通，原因是两条硬约束：

1. **供应商要直接下载素材**。`tryon/index.ts:295-296`、`:445`、`:554` 会把
   `garment.flat_image_url` 原样交给万相 / Aidge / Replicate，`user-photo` 也一样
   （`person_image_url`）。桶一旦私有，这些公网 GET 全部 400，试衣整条链路断掉。
2. **历史商品图躺在 `user-photos` 根目录**（`garment-N-1536.jpg` × 6）。
   想搬到 `garments` 桶必须先能写 —— 实测匿名/普通登录上传被 RLS 403
   （`new row violates row-level security policy`），而搬文件需要 service_role。

所以采取**渐进式收口**，把风险控制在「新增数据立即私有，存量数据后续清理」：

| 桶 | 现状 | 说明 |
|---|---|---|
| `user-media`（新） | **private** | 新的全身照都进这里，只有本人 + 服务端可读 |
| `user-photos`（老） | public | 只剩 6 张历史商品图 + 旧任务的全身照，作为素材桶保留 |
| `tryon-results` | public | 生成结果；`/video` 要把首帧 URL 交给万相，等函数改成服务端自签再收 |
| `inspiration-posts` / `garments` / `poses` | public | 本来就是公开内容（社区流、商品素材） |

### 10.3 落地内容

**数据库**（`supabase/migrations/016_storage_private_buckets.sql`，独立执行清单
`supabase/manual-apply-016-private-storage.sql`）

- 建桶 `user-media`：`public = false`、`file_size_limit = 15MB`、
  `allowed_mime_types = jpeg/png/webp/heic/heif`（把大小与类型校验放到桶级，省一次应用层判断）。
- 四条 owner 策略（read / insert / update / delete），统一按
  `(storage.foldername(name))[1] = (select auth.uid())::text` 校验首段目录。
- `on conflict (id) do update`，可重复执行。

**客户端**（`src/lib/supabase.ts` 新增「私有存储的访问票据」一节）

- `parseStorageUrl(url)`：从任意形态的 Storage URL 取出 `{bucket, path}`，
  同时兼容 `/object/public/`、`/object/sign/`、`/object/authenticated/` 三种前缀 ——
  这样「库里存了带 token 的旧值」也能解析出真实路径。
- `canonicalStorageUrl(url)`：把签名链还原成不带 token 的规范地址（存库、比通用）。
- `signStorageUrl(url)`：公共桶原样返回；私有桶换 1 小时签名地址。
  带**内存缓存**（提前 5 分钟续签）和**并发去重**（同一张图只签一次）。
- `resolveDisplayUrl` / `resolveDisplayUrls`：前者单张、后者走 `createSignedUrls` 批量，
  失败一律降级返回原地址 —— 宁可裂一张图，也不让整页崩。
- `fetchTryonTask` / `fetchVideoTask` / `fetchTryonHistory` 统一过 `withSignedMedia()`，
  把 `user_photo_url` / `first_frame_url` / `result_url` 换成可显示的地址；
  历史列表一次性批量签名，避免首屏打十几条签名请求。
- `createTryonTask`：发给 Edge Function 的 `user_photo_url` 先换成签名地址
  （服务端要能直接下载），库里存的是规范地址，所以不会因为 token 过期变成死链。
- `deleteTryonTask`：桶名不再写死，从 URL 里解析（老记录 `user-photos`、新记录 `user-media`）；
  判断「这张照片是否被其它任务共用」也改成比较**规范地址**，
  否则签名 token 不同会被误判成两张图，导致删掉别人还在用的照片。

## 十一、私有桶上线后的一次完整联调（发现两个真问题）

存储私有化只做完「新桶 + 签名」这一半是不够的，必须真的走一遍「上传 → 试衣 → 出图」。
这次联调是用无头浏览器驱动真实点击完成的（CDP `selectFile` 拦截文件选择框），
所以走的是和用户完全一样的代码路径，不是接口探针。

### 11.1 发现的问题一：客户端超时比供应商还短，用户看到「失败」但后台其实成功了

第一次跑：界面显示「试衣生成失败，请重试」。查库发现那条任务 `status = done`。

根因：我在 P1-3 里给 `createTryonTask` 加的 `timeout: 20_000` 比供应商还短。
`/tryon` 是**同步**接口——Edge Function 要等 Aidge 把图生成完才返回，
实测 40–70 秒（供应商侧超时上限 90 秒）。20 秒一到客户端就 abort 并报错，
服务端那边还照常跑完、照常扣费。

修复（`src/lib/supabase.ts`）：

```ts
const TRYON_CREATE_TIMEOUT_MS = 180_000; // 必须长于供应商 90 秒上限
...
if (error) {
  const message = await getFunctionErrorMessage(error as FunctionInvokeError);
  if (/timeout|timed out|abort/i.test(message)) {
    throw new NetworkError('生成还在后台进行，请稍后到「我的」查看结果');
  }
  throw new Error(message);
}
```

教训记一笔：**「加超时」不是无脑加**。异步轮询型接口（`/video`）超时给短是对的，
同步生成型接口（`/tryon`）的超时必须 ≥ 供应商上限，否则就是「假失败 + 真扣费」。

### 11.2 发现的问题二：全身照预览把照片裁掉了一半

原来的预览是固定 200 高 + 默认 `cover`，竖构图的全身照会被裁成中间一条——
而试衣最要紧的恰恰是「构图对不对、有没有拍到脚」。

修复（`src/app/(tabs)/tryon.tsx`）：预览容器 200 → 260 高、底色用 `surfaceAlt`、
`<Image resizeMode="contain" />`，整张照片完整可见，留白也看得出来。

### 11.3 修复后的结果

- 第二跑：界面正常进入「03 试穿结果」段，出现「换成动态 / 选姿势 / 生成穿搭视频 / 再试一次」；
- 「我的」页显示 **2 条已完成记录**，缩略图都是真实生成的模特上身图（截图 `37-profile-with-result.png`）；
- 这同时反证了**私有桶链路是通的**：Aidge 拿到的 `ModelImageUrl` 是我传的
  `.../storage/v1/object/sign/user-media/<uid>/<file>.jpg?token=...`（约 900 字符带鉴权），
  它能直接下载并出图，说明「签名地址交给供应商」这条路可行，不需要退回公开副本。
- 花费：两次真实生成约 ¥0.8（Aidge 约 ¥0.4/张），预算 ¥2.5 内。

### 11.4 现在的完整链路（已验证）

```
选图 → canvas 压到 2049/jpeg 0.88 → 上传私有桶 user-media/<uid>/
     → 客户端 createSignedUrl(1h) 用于自身预览
     → createTryonTask 再把规范地址换一次签名地址交给 Edge Function
     → Aidge 直接 GET 该签名地址（等价于无鉴权下载，已实测 200 image/jpeg）
     → 结果转存 tryon-results（公开）→ 轮询 → 「我的」列表
```

## 十二、任务不丢：离开页面也能继续

### 12.1 问题

试衣是同步接口（40–70 秒），视频更久（实测排队 25 分钟，客户端上限已放到 30 分钟）。
这期间用户切 Tab、切走浏览器、甚至断网重进，之前的界面是**一片空白**：
他既不知道任务还在跑，也看不到已经生成好的图，于是再点一次——
既重复扣费，还可能覆盖掉已经生成好的视频。

### 12.2 实现

新增 `src/lib/inflight.ts`（单槽位）：

```ts
type InflightTask = { taskId: string; kind: 'tryon' | 'video'; label: string; startedAt: number };
saveInflight / loadInflight / clearInflight   // AsyncStorage key: inflight.task.v1
```

- `startTryon` / `startVideo` 一创建任务就 `saveInflight`，走到终态 `clearInflight`；
- 试衣页挂载时 `loadInflight()`，如果有记录就**自动接管轮询**：
  试衣任务直接补出结果图；视频任务先 `fetchVideoTask` 取回 `first_frame_url`
  把结果区填上，再继续轮询视频；
- 超过 40 分钟的记录视为失效（服务端有超时兜底，不必无限追）；
- 顺手把视频轮询抽成 `pollVideo(taskId)`，首次生成和恢复共用一份逻辑。

### 12.3 验证方式（零成本）

没有再次花钱生成：直接往 `localStorage['inflight.task.v1']` 塞一条**已完成**的历史任务，
刷新 `/tryon` 后页面自动进入「03 试穿结果」段并渲染出结果图，随后该键被清空
（`inflight: null`）—— 说明「读记录 → 接管 → 出结果 → 清理」整条链路通。

### 12.4 视频函数改为服务端自签首帧

`supabase/functions/video/index.ts` 新增：

```ts
const PRIVATE_BUCKETS = new Set(["tryon-results", "user-media", "user-photos"]);
function parseStoragePath(url) { ... }
async function toFetchableUrl(url) {
  // 私有桶用 service_role 现签 1 小时直链；公开桶原样返回，不额外发请求
}
...
const firstFrameUrl = await toFetchableUrl(task.first_frame_url);
input: { img_url: firstFrameUrl, prompt }
```

这样 `tryon-results` 收私有之后，万相依然拿得到首帧图。
客户端 `PRIVATE_BUCKETS` 也已加上 `tryon-results`，bucket 变私有的那一刻不用改代码。

## 十六、存量照片迁移（user-photos → user-media）

### 16.1 为什么要单独写一个 Edge Function

`user-photos` 不能直接置私有：同一桶根目录还有 6 张商品平铺图，供应商要直接下载。

### 16.2 演练与实跑

| | 演练 | 实跑 |
|---|---|---|
| 桶内对象 | 8 | 8 |
| 商品图（跳过） | 6 | 6 |

| 删除源对象 | 0 | **2** |
| 失败 | 0 | **0** |

搬的是 `test-person-1.jpg`（4 条引用）、`test-person-1-2048.jpg`（9 条引用）。

### 16.3 迁移暴露的路径-策略不匹配（019）

016 给 `user-media` 的读策略是「路径首段 = uid」，而这两张历史文件在**根目录**，路径里没有 uid
—— 谁也不签名成功，13 条记录的缩略图会裂。

019 把读/删判定的语义改成「**这张图被我自己的一条试穿记录引用**」（与 018 对 tryon-results 一致），
保留原有的「首段 = uid」分支用于「任务行还没建出来时预览刚上传的照片」：

```sql
bucket_id = 'user-media' and (
  (storage.foldername(name))[1] = (select auth.uid())::text
  or exists (select 1 from public.tryon_tasks t
              where right(t.user_photo_url, length(name)) = name
                and t.user_photo_url like '%/user-media/%'
                and (t.owner_user_id is null or t.owner_user_id = (select auth.uid())::text))
)
```

写策略不动（上传/覆盖仍限自己的目录）。

## 十七、真机反馈的两个问题（2026-11-17 记录，待处理）

### 17.1 视频能播，但「选项都是空白」

用户截图里，卡片区域有一块纯灰条，右侧露出「奶白针织长袖 / 上装 / 已完成」——即
「我的」页的记录卡片里，**缩略图区域是空的**（灰底占位），而不是文字没了。

最可能的原因（按概率排序）：

1. **迁移后的照片签名失效**。存量迁移把 13 条记录的照片搬到了 `user-media` **根目录**
   （`test-person-1.jpg`），路径里没有 uid；019 用
   `right(t.user_photo_url, length(name)) = name` 反查归属。这条匹配对
   「URL 里带查询串」或「文件名被 URL 编码」的情况会失配，签不出图 → 卡片空白。
2. **视频记录的封面**取自 `first_frame_url`，如果该对象在 `tryon-results/<task>/` 下但
   任务行的 `owner_user_id` 与实际会话不一致，018 的 owner 策略同样会让签名 404。
3. 主题切换后 `useThemedStyles` 复用旧样式（可能性最低，因为文字正常）。

处置方式：先用「我的 → 任一条空白记录」拿到该行的 `user_photo_url` 与任务 id，
在页面上下文跑一次 `createSignedUrl`，看是 200 还是 404，再决定是修匹配规则还是
把存量文件重排到 `<uid>/` 目录。**待网络恢复后执行**（当前 Supabase 全部端点 0.6 秒
内 `Failed to fetch`，连 `rest/v1/garments` 都失败，无法验证）。

### 17.2 生成的视频「太僵硬、没动作」，想要动作参考库

根因已经比较明确：**我们给万相的运动提示词太弱**。现在 `poses.pose_desc` 是静态描述
（例如 `The model stands naturally and gently shifts weight to show the outfit clearly.`），
而按[阿里云万相提示词指南](https://help.aliyun.com/zh/model-studio/text-to-video-prompt)，
图生视频的公式是：

> 提示词 = 运动 + 运镜

也就是说 I2V 场景里模型已经知道主体和场景，**唯一需要描述的就是「怎么动」和「镜头怎么动」**。
我们现在两样都没给，模型只能做最小幅度的形变 → 看起来就是「站着微微晃」。

**方案（三层）**：

| 层 | 做法 | 成本 |
|---|---|---|
| 立即可用 | 把 `poses.pose_desc` 改写成「运动 + 运镜」句式，并补 3 个更有戏的动作（转圈、行走回头、撩发） | ¥0，一条 SQL |
| 中期 | 姿势库从「3 条文案」升级成「带封面图 + 分类（站姿/行走/转圈/回头）」的可选动作卡，用真实模特图做封面 | 需要 6–10 张动作参考图 |
| 长期 | 接姿态驱动（pose-driven I2V），用骨架序列控制动作，而不只是文字 | 换模型，成本高 |

可直接借鉴的开源参考（用户要求「抄 GitHub 上的动作库」）：

- [HRuiCcc/RuiC-PoseAtlas](https://github.com/HRuiCcc/RuiC-PoseAtlas)：288 组人体姿态 × 5 视角，
  纯静态站，姿态可直接当「动作参考图」给用户看
- [FireRedTeam/DynamicPose](https://github.com/FireRedTeam/DynamicPose)：姿态序列驱动人像动画，
  大动作泛化好，是「中期→长期」的跳板
- [CloudEngineHub/MusePose](https://github.com/CloudEngineHub/MusePose)：AnimateAnyone 的开源复现，
  姿态驱动虚拟人生成
- [EquiFashion-DB](https://huggingface.co/datasets/NguyenDinhHieu/EquiFashion-DB)：
  含 image/text/pose 对齐的时尚数据集，适合做姿态+穿搭联合参考

注意：这些是**姿态驱动**方案，和当前「万相文生视频 + 文本提示」不是一条链路。
先用第一层（改提示词）验证「动作幅度是否够」，再决定要不要上姿态驱动。

## 十八、一键成套出视频 / 收藏搭配可点开 / 缩略图不再空白

### 18.1 搭配页「出视频」：一次点击跑完三件套再出片

原来要从搭配页点「试穿这套」→ 试衣页再点「依次试穿 N 件」→ 等三次生成 → 再点「换成动态」，中间五六个动作。

```ts
useEffect(() => {
  if (!autoVideoRef.current) return;
  if (!resultUrl || !resultTaskId || generating || generatingVideo) return;

}, [resultUrl, resultTaskId, generating, generatingVideo]);

const savedOutfits = useMemo<Outfit[]>(() => {

  const all = buildOutfits(garments, {});
  return favorites.looks
    .map((id) => all.find((outfit) => outfit.id === id))
    .filter((outfit): outfit is Outfit => Boolean(outfit))
    .slice(0, 8);
}, [garments, favorites.looks]);
```

卡片点进去直接带 `look` + `lookTitle` 到试衣页，和搭配页的入口行为一致。

`supabase/manual-check-thumbnails.sql` —— 纯查询、不改数据，一次性回答

## 十九、视频「更多选项」弹层空白

用户真机反馈：「这个更多选项弹出来的选项全是空白的」，附截图 —— 视频缩略图上有一个半透明圆形
⋮ 按钮 + 底部进度条。

### 19.1 定位：不是我们的 UI

那个 ⋮ 和进度条是**浏览器原生 `<video controls>` 的控件**（`ResultVideo` 里 `nativeControls`）。
弹层里的「循环播放 / 下载 / 播放速度 / 画中画」由 UA 样式渲染，页面管不到。

根因：系统深色模式 + App 浅色主题的组合下，原生控件继承了 `color-scheme: dark`，

## 二十一、换模型能不能「一次出整套」+ 两个零成本优化（2026-11-17）

### 21.1 调研结论：换模型解决不了「一次多件」，只解决「质量 / 姿势控制」
逐个查了主流商业接口的入参：

| 服务 | 入参 | 是否一次多件 | 单价 |
|---|---|---|---|
| Aidge AiTryOn（现用） | 人像 + 1 件 | 否 | ≈ ¥0.4 / 张 |
| [fal · Leffa](https://fal.ai/models/fal-ai/leffa/virtual-tryon) | `human_image_url` + `garment_image_url` + `garment_type`(upper/lower/dress) | **否** | $0.1 / 次 ≈ ¥0.72 |
| [FASHN Try-On Max](https://docs.fashn.ai/guides/tryon-parameters-guide) | `product_image` + `model_image` | 否 | 按张计费 |
| [OOTDiffusion](https://replicate.com/qiweiii/oot_diffusion_dc) | `garment_image` + `garment_category` | 否 | 按 GPU 秒计费 |
| 社区 Leffa fork | 额外支持 `garment2_image` + `pose_image` | 部分（两件） | 质量未验证 |

结论：**换商业模型不会把「三件」变成「一次调用」**，只会换质量与单价；三件套用 Leffa 反而更贵（¥2.16 vs ¥1.2）。真·一次多件只有两条路：① 自建 ComfyUI 流水线（Leffa DC + 多件 mask 合流 + openpose/densepose），GPU 月成本与运维都不是「省钱」方向；② 用社区 fork 的两件入参，质量与稳定性无保障。

**真正值得换的点**：Leffa 的 `pose_transfer`（人像 + 目标姿势图 → 同一个人换姿势）。这才是「姿势参考图」的正解，但单价 ¥0.72/次，只能作为**付费可选档**，不能替代现在的免费方案。

### 21.2 优化一：试衣页「用今日搭配」一键带入

- 意义：新用户不用理解「上装 → 外套 → 下装」的顺序，点一下就有可试的一套。

### 21.3 优化二：本地姿势示意图
- 生成 6 张 300×400 线稿姿势图（自然站姿 / 迈步 / 转身回望 / 手插口袋 / 侧身 / 撩发），随包分发在 `assets/poses/`，用 `require()` 静态引入 `POSE_DIAGRAMS`。

## 二十二、背面死角：问题定性与三档方案（2026-11-17，方案待批）

### 22.1 问题定性
试衣模型（Aidge AiTryOn）只输出**一张正视图**。视频里让模特「转身」时，背面是模型根据单张正面图**推断**出来的——褶数、后背剪裁、拉链位置都可能与实物不符。对服装设计师而言，错误展示比不展示更糟。

### 22.2 三档方案

| 档 | 做法 | 成本 | 解决程度 |
|---|---|---|---|
| A | 结果图/视频标注「AI 生成 · 背面为推测」 | ¥0 | 只是诚实，不解决问题 |
| B | `garments` 加 `back_image_url`；素材管理分「正面/背面」两个上传位；试衣页加「看背面」→ 人像不变、用背面图再跑一次 | +¥0.4/件（仅在使用时） | **真实背面**，幻觉只剩正侧过渡 |
| C | 多视角重建（Zero123 类）或要求品牌提供 3D 资产 | 高 | 完整三维，但超出当前预算 |

### 22.3 为什么推荐 B 而不是换模型
- 主流 try-on 接口（Aidge / Leffa / FASHN / OOTDiffusion）全部是「一张人像 + 一件衣服 → 一张图」，**没有哪个商业接口能一次输出多视角**。
- 所以「背面」不是模型能力问题，是**素材完整度问题**：给两张图就能出两个真实视角，这是唯一在现预算内成立的做法。
- 结论：**素材越全，幻觉面积越小**。

### 22.4 落地清单（批了就做，预计改 4 个文件）
1. `supabase/migrations/021_garment_back_image.sql`：`alter table public.garments add column if not exists back_image_url text;`
2. `src/app/(tabs)/admin.tsx`：上传区拆成「正面平铺 / 背面平铺」两个位，背面可留空。
3. `src/lib/supabase.ts`：`Garment` 类型加 `back_image_url`，`GARMENT_FIELDS` 同步，缺列自愈。
4. `src/app/(tabs)/tryon.tsx`：结果区加「看背面」（仅当所选单品有 `back_image_url` 时出现）→ 用该图再跑一次 `createTryonTask`，结果并列展示，标注「背面」。

## 二十三、视频链路实测：动作/转身成立，并揪出「10 分钟误杀」的真 bug（2026-11-17）

### 23.1 任务与花费
- 任务 `3d129b4b-f107-4916-b8be-b7c5793a30eb`，`duration: 5`、默认 `background: keep`、`show_back: true`。
- 花费约 ¥0.3–0.4。**如果不是下面这个 bug，这钱就白花了。**

### 23.2 实测结果（逐帧）
| 时间 | 画面 |
|---|---|
| 0.15s | 正面站定，裙子与裤子的层次、褶皱与输入帧一致 |
| 1.4s | 重心微移 + 半步向前，布料自然垂落 |
| 2.6s | 侧身 3/4，镜头缓慢推近，**背景仍是同一块影棚布** |
| 3.8s | 完整背对镜头，可见裙背分割线与褶裥 |
| 4.85s | 背面定格（按要求保留最后一秒） |

- 结论：**单向转身 + 运镜 + 锁背景** 三项都成立；没有多手多脚、没有衣服融化、没有换人。视频时长 5.007s、744×1238、2.2MB、`content-type: video/mp4`、魔数 `ftyp`，签名地址免鉴权 GET 200 可播。
- **但背面细节是模型推断的**：背面出现的前后分割线与褶裥在正面平铺图里并不存在。这正好印证第二十二节的判断——背面不是模型能力问题，是素材完整度问题。要真实背面，走 B 档（`back_image_url` + 再跑一次）。

### 23.3 揪出的真 bug：服务端 10 分钟超时把成功的视频判死
- 现象：提交后约 23 分钟我去轮询，任务直接变成 `status=timeout`、`error_msg="视频生成超时，请稍后重试"`。
- 根因（`supabase/functions/video/index.ts` 旧代码）：超时判断写在**查询供应商之前**，且阈值 `VIDEO_TIMEOUT_MS = 10 分钟`。万相排队实测能到 20–25 分钟，于是「视频已经生成好了，第 10 分钟之后的第一次轮询就把它判死」。
- 修复（已部署 v22）：
  1. `VIDEO_TIMEOUT_MS` 10 分钟 → **30 分钟**，与客户端 `MAX_VIDEO_WAIT_MS` 对齐；
  2. 把超时判断挪到**查询供应商之后**：先问万相，`SUCCEEDED` 就照常转存；`PENDING/RUNNING` 且超时才收尾；连 `provider_task_id` 都没有或请求抖动时，也只在超限后才收尾（抽成 `markTimeout()`，只在一处写 timeout）。
- 抢救：把该任务的 `status` 重置为 `processing`、`stage_started_at` 刷新后再轮询一次 → 供应商其实早完成了，函数立刻转存并写成 `done`，视频拿回来了（也因此有了 23.2 的逐帧证据）。

### 23.4 附带修正：姿势描述与通用动作段打架
- 姿势库改写后，`pose_desc` 里既有动作也有 Camera 句，再拼上通用「走两步 + 转身」段，两段动作互相抵消（症状：原地摇晃、动作半途卡住）。
- 修复：`stripCamera()` 剥掉姿势里的 Camera 句（运镜只由我们统一控制）；有姿势时动作段只补一句「结尾转身并定格」，不再追加通用动作段。
- 已部署 v21 起生效。

### 24.2 实测：把背面平铺图当衣服图喂进去，得到的是「穿反」
- 用「鼠尾草绿亚麻连衣裙」的**背面图**（`backtest-*.jpg`，从视频背面帧裁的）跑一次真实试衣（任务 `5b4a13f8-3687-4414-8114-4205ed3833ea`，约 ¥0.4）。
- 结果（`42-backview-result.png`）：**人物仍然正面朝镜头**，但身上那条裙子的**背面裁片（中缝 + 腰部褶裥）被贴到了正面** —— 看起来像把裙子反着穿。
- 根因：Aidge `AiTryOn` 的输入是 `ModelImageUrl` + `ClothImageUrl` 两张图，语义是「把这件衣服穿到这个人身上」，模型把衣服图当作**正面视图**去映射到躯干；它没有「反穿 / 背对镜头」的概念。换哪家单图 try-on（Leffa / FASHN / OOTDiffusion）都是同一个结构。
- 所以结论是：**「背面图 → 再跑一次就得到真背面」这条设计不成立**。链路（字段/上传/传参/400 分支）都通了，但产品语义错了。

### 24.3 改成什么（已改，零成本、更诚实）
- 「看背面」从「AI 生成背面」降级为「**展示实物背面图**」：
  - 按钮文案：`看背面实物图` / `收起背面实物图`（纯开关，不再调接口、**不花钱**）；
  - 展开后显示 `back_image_url` 原图 + 说明「实物背面图 · 由「XX」的素材提供。AI 试穿只还原正面视角，背面细节以这张实物图为准。」
  - 对设计师来说，真实背面图比模型编的背面有用得多；对用户来说，也不会被误导。
- 服务端 `use_back` 分支**保留**（注释写明用途）：将来换成支持多视图的供应商（如 FASHN 的 `tryon-v1.6` 系列、或多图 conditioning 的自建模型）时可以直接复用，不用再改协议。
- 截图：`43-backref.png`（展开态）。

### 24.4 真正的「背面」还有两条路（按性价比）
1. **视频转身**（已实测成立，第二十三节）：5 秒视频里 3.8s 起就是完整背面，用户能看清廓形与摆动；成本约 ¥0.3–0.4，且本来就是「锦上添花」的卖点。
2. **商家提供背面图 + 我们的视频/图只做正面**：把背面图放在详情里给设计师与买家看，明确标注「AI 试穿只还原正面」。

### 28.3 顺带修掉一个真 bug：新设备上天气永远「不可用」

静态站跑起来后，第一眼就看到天气 chip 是「天气不可用」。查下去是两条原因叠加：

1. **冷却时间给太长**：网络类失败也按 1 小时冷却，而线路抖动通常几分钟自愈 → 供应商恢复了，界面还在拒绝重试。
2. **「全冷却 + 无快照」时直接放弃**：三个供应商都在冷却、本地又没有旧快照，代码直接返回 null，用户永远看不到天气。

修法：
- 网络类失败冷却降到 **20 分钟**（`WEATHER_FAILURE_COOLDOWN_MS`）；
- 新增 `allowRetry`：`所有供应商都在冷却 && 没有旧快照` 时**无视冷却，把所有供应商全量重试一遍**（不是只试第一个就退出，第一版就是这么写错的）。

修完实测：新 origin 首屏从「天气不可用」变成 **18° 阴**（`weather.snapshot.v1` 落盘、`open-meteo` 命中）。

### 28.4 一个方法论教训：node 探针通 ≠ 浏览器能用

想加第三个天气源时，我用 node 探 `https://www.7timer.info/...` → **200 / 2.5s**，看起来比 wttr.in（4.5s）还好。结果写进代码后浏览器里直接 `TypeError: Failed to fetch` —— 是 **CORS**：7timer 不返回 `Access-Control-Allow-Origin`。

同一批探针里 `open-meteo` 用 node 连续两次 9 秒超时，但浏览器里 **200 / 1.0s**。也就是说：**两个方向的误判都发生过**。

结论（已写进 `src/lib/weather.ts` 顶部注释）：**「能不能通」必须用页面上下文验证；node 探针只能证明网络可达，证明不了浏览器可用。**

### 29.4 顺带修掉的一个真 bug

演示模式第一次跑通后，页面右上角弹出 React 红框：`Encountered two children with the same key`。
根因不是我新写的循环，而是**旧代码里用 url 当 key**：`completedSteps.map((item) => <View key={item.url}>)`。真实链路里每件的 url 都不同所以从没暴露；演示模式只有 2 张样例、3 件单品，第 1 和第 3 件取到同一张图 → key 重复。

## 三十、串行试穿可取消 + 结果保存到本地

### 30.1 为什么先做这两件

一次选 3 件是「依次试穿」：每件 40–70 秒，三件就是 **3 分钟左右**。这期间界面只有一个
进度条和「请勿离开」，点错了、换主意了都没法退出——实测自己演示时也被卡住过。这是
可用性问题，不是功能缺失。

第二个是「跑完的东西拿不走」：结果图/视频在私有桶里，页面上是 1 小时有效的签名地址，
用户想存下来只能截图。对「试完想发朋友圈/发给朋友看看」这个真实动作来说，缺了最后一厘米。

### 30.2 取消：只停前端，不打断已花的钱

关键取舍：服务端那一张**已经在跑**，钱也扣了、图也会出来。所以取消的语义定成
「停止继续叠加 + 停止轮询」，而不是「回滚」：

- `cancelRef` 只影响前端：`pollTryon` 下一轮直接返回 `null`，串行 `for` 立刻 `break`；
- **不删任务、不清 inflight** —— 用户回来还能在「我的」看到这件已经生成好的；
- 刚生成完的那几件保留在结果区，配一句「已取消：先完成的 N 件保留在结果里」；
- 一件都没跑完时提示「那一件可能仍在后台生成，稍后到「我的」看看」，避免让用户以为没花钱。

顺带修了一个自己写的边界：取消动作如果恰好落在最后一件**已经完成之后**，原来会误报
「已取消」——现在只在 `done.length < chain.length` 时才提示。

### 30.3 保存到本地：三条路都试过，只有一条能走

| 方案 | 结果 |
|---|---|
| `<a download href="远端签名地址">` | 跨域时 download 属性被忽略，浏览器改成新标签打开 |
| 让存储端回 `Content-Disposition: attachment` | 本项目 storage 版本忽略 `?download=`（签名接口的 download 选项也不生效）：签名 URL 里没有该参数，GET 响应头也没有 content-disposition |
| fetch 成 Blob → objectURL → `<a download>` | 可用：文件名正确、不依赖跨域头 |

所以 `src/lib/download.ts` 走第三条：`fetch` → `blob` → `createObjectURL` → 隐藏 `<a download>`
点一下 → 10 秒后 `revokeObjectURL`。文件名形如 `ai-chuanda-<任务前 8 位>-20261117-2104.jpg`。
原生端不实现（存相册要额外的媒体库权限流程），文案直接给「截图或录屏保留」。
已知边界写进注释：Safari/iOS 对非手势触发的下载会改为打开图片，此时提示长按保存。

### 30.4 怎么验证的（含一个诚实的空白）

- 取消：`?demo=1` 点「依次试穿 3 件」→ 第 1 件跑完后点「取消」→ 结果区保留 1 件 +
  提示「已取消：先完成的 1 件保留在结果里。」；进度卡消失，按钮回到「再试一次」。
- 保存：给页面挂一层探针（拦截 `HTMLAnchorElement.prototype.click` 与 `URL.createObjectURL`），
  点「保存图片到本地」后拿到 `{ name: "ai-chuanda-tryon-20261117-2104.jpg", blob: { size: 2635654, type: "image/jpeg" } }`
  —— 证明「取到字节 → 造本地链接 → 带上正确文件名触发下载」这条链路通。
- **空白**：无头浏览器不会把下载写到磁盘（连 `data:` URL 的下载也不落盘，属运行环境限制），
  所以「文件真的出现在下载文件夹」这一步只能由真实浏览器验证，这里不下结论。
